# Debug 工作流

## 触发条件

只在用户明确要求时启用，例如：

- `使用 debug skill`
- `使用 debug workflow`
- `请走 debug 工作流`
- `启动本地日志服务器帮我排查 bug`

如果用户没有显式要求，不要默认启用。

## 目标

该 skill 用于把浏览器侧调试信息稳定写入一个临时 log 文件，再由当前 agent 基于该文件排查问题。

在同一个 debug 会话中：

- 始终复用同一个 log 文件路径
- 每次新的用户追加提问前，先清空旧日志
- 用户确认修复后，删除日志文件与后台服务

## 核心原则

### 证据优先

一旦进入 debug workflow，日志不是可选参考，而是默认的一手证据来源。

这意味着：

- 在读取当前最新日志前，不要直接根据代码逻辑下结论
- 在日志证据不足时，先补采日志或补打点，再继续分析
- 代码阅读的作用是解释日志、定位实现位置、验证修复，不是替代日志猜测根因

### 明确区分“观察”与“推断”

对用户汇报时，先给出日志里已经观察到的事实，再说明基于这些事实的推断。

至少要明确区分：

- `日志证据`：来自 `show` 或 `log_file` 的具体报错、事件顺序、状态值、接口响应
- `分析推断`：基于这些证据映射到的代码路径、可能根因、修复方案

如果当前还没有拿到有效日志，就不要把“猜测”包装成“定位结果”。

### 修复前必须完成证据闭环

进入修复之前，必须已经拿到能够证明判断成立的打印信息或日志数据。

也就是说：

- 不能单纯因为代码逻辑“看起来像这里有问题”，就直接开始修复
- 必须先从日志、打印、请求记录、状态快照、报错堆栈中拿到支持该判断的数据
- 只有当这些数据能够解释“问题是怎么发生的”时，才可以进入正式修复

如果当前证据还不足，允许做的下一步是补日志、补打点、要求重新复现；不允许把代码修改当成“验证猜想”的第一手段。

## 标准流程

### 1. 启动会话

首次进入该 workflow 时，优先执行：

```bash
.claude/skills/debug/bin/debug-session.sh start
```

如需显式命名会话，可加：

```bash
.claude/skills/debug/bin/debug-session.sh start --session <topic-slug>
```

读取返回 JSON 中的：

- `endpoint`
- `clear_url`
- `log_file`
- `server_log`

随后把 `endpoint` 提供给用户，指导浏览器或页面脚本把调试信息写进去。

### 2. 先获取一份新的可用日志

启动会话后，如果当前还没有围绕该问题的新日志，先要求用户复现并写日志，再继续分析。

在这一步之前：

- 不要跳过日志采集直接开始读代码给结论
- 不要只因为服务已经启动成功，就假设已经具备了排障证据

至少应确认以下信息已经进入日志：

- 复现动作或触发路径
- 关键报错 / warning / failed request / 状态异常
- 能帮助定位上下文的必要字段，例如页面 URL、接口名、参数、返回值、堆栈、关键状态

### 3. 新一轮提问前清空旧日志

如果用户在同一个排障线程里追加问题、补充复现条件、或要求“重新看一下”，先执行：

```bash
.claude/skills/debug/bin/debug-session.sh reset
```

然后再让用户重新操作页面、重新写日志。

不要把上一轮遗留日志和本轮新问题混在一起分析。

### 4. 读取日志并排查

优先使用以下命令读取当前日志：

```bash
.claude/skills/debug/bin/debug-session.sh show
```

如果需要更多元信息，再执行：

```bash
.claude/skills/debug/bin/debug-session.sh status
```

必要时直接读取 `status` 返回中的 `log_file`。

读取日志后，先完成这两个动作，再进入代码定位：

1. 提炼 `日志证据`
   - 明确报错文本、异常时序、失败接口、异常状态值
   - 若可能，引用关键片段或指出几条最相关的日志记录
2. 基于证据决定下一步
   - 如果日志已经足够指向某段实现，再去读代码验证并修改
   - 如果日志还不够，先补充日志字段或补充复现，再继续

只有在完成上面两步之后，才应进入“根据代码实现解释根因”的阶段。

在正式修改代码前，还应再确认一次：

- 当前打印信息是否已经能证明这次判断成立
- 当前修复是否能回扣到这些打印信息中的异常现象

如果答案是否定的，先继续补证据，不要提前修复。

### 5. 用户确认修复后清理

当用户明确表示问题已修复、无需继续保留日志时，执行：

```bash
.claude/skills/debug/bin/debug-session.sh cleanup
```

这一步必须删除 log 文件、状态文件和后台微型服务器，避免残留临时调试数据。

## 行为约束

进入该 workflow 后，遵循以下约束：

1. 不能把“我看了代码，感觉这里像有问题”当作首轮排查结果。
2. 不能在没有读取最新日志的情况下直接给出根因判断，除非你明确说明“当前尚无有效日志，下面只是临时猜测，不作为定位结论”。
3. 如果最新日志信息不足，下一步优先是要求用户补充复现或指导补打点，而不是继续扩大代码阅读范围。
4. 在打印信息或日志数据尚未证明判断正确之前，不能开始正式修复；此时只能继续取证。
5. 修复方案必须能回扣到日志中的异常现象，至少解释“为什么这份日志会出现这个结果”。

## 推荐输出骨架

在 debug workflow 中，尽量按这个顺序对用户汇报：

1. `我先看了最新日志`
2. `日志里已经确认的现象`
3. `基于这些现象，我准备去看的代码路径`
4. `这些打印信息为什么足以支持当前判断`
5. `如果证据还不够，需要补什么日志`

这样可以减少“服务开了，但排查仍然脱离日志”的情况。
